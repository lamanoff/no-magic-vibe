Зачем это нужно

#

Большой запрос «сделай приложение» неизбежно сломается: агент сгенерирует слишком много кода, часть окажется неправильной, и вы не поймёте, где именно. План из 6–10 задач — способ резать работу на куски, каждый из которых заканчивается видимым результатом. Меньше кода за раз — меньше ошибок за раз, и каждую легче локализовать.

»

Что мы делаем

#

Превращаем spec из урока 1.1 в docs/plan.md: упорядоченный список из 6–10 задач. У каждой — что делаем, как проверить готовность, какие файлы затрагиваются.

1

Шаг 1. Откройте spec и перечитайте раздел «функции»

#

План делается из спеки, не из головы. Каждая функция из spec должна найти место в плане; каждая задача плана должна вести к какой-то функции из спеки. Задача, которая не ведёт к функции, — это раздувание, которое вы пропустили в уроке 1.1.

2

Шаг 2. Попросите агента разбить работу

#

Промпт ниже. Агент знает типовые этапы (каркас → данные → поведение), но порядок задач — ваша зона ответственности: проверьте его, а не примите как есть.

Отдельно сверьте первые три задачи с курсом: уроки 2.1–2.3 идут по порядку «экран питомца → сохранение состояния → спад и эмоции». Если агент поставил их иначе — поменяйте порядок или переформулируйте задачи, чтобы совпало.

3

Шаг 3. Проверьте каждую задачу по трём вопросам

#

Для каждой задачи ответьте: 1) виден ли результат — в браузере или в терминале (сборка, тесты)? 2) есть ли критерий готовности, который можно проверить кликом или взглядом? 3) не зависит ли задача от той, что стоит после неё? Задача без видимого результата, вероятно, слишком мелкая: объедините её со следующей.

И отдельно: задача-предпосылка (создать проект, поставить тесты) не ведёт к функции, но без неё не собрать остальное. Такие задачи допустимы — если они короткие.

Если задач получилось меньше шести или больше десяти — не принимайте список как есть: попросите агента объединить мелочи или разбить слишком крупные задачи.

Промпт для агента 
Открой docs/spec.md. Разбей работу на 6–10 маленьких задач
в порядке выполнения и запиши их в docs/plan.md.

Для каждой задачи укажи:
1) что делаем;
2) как проверить, что готово — в браузере или в терминале;
3) какие файлы затрагиваются.

Каждая задача должна давать видимый результат. Задачи-
предпосылки (создание проекта, установка тестов) помечай
отдельно и делай короткими.

Код не пиши — только план.
!

Что может пойти не так

#
  1. Пропущенные зависимости. Агент ставит «настроить проект» последней задачей или забывает, что «сохранять состояние» нельзя сделать раньше «показывать состояние». Почему: порядок задач модель воспроизводит по частому шаблону (каркас → данные → поведение), а не выводит из вашего проекта. Поэтому порядок проверяете вы — вопросом: «можно ли выполнить эту задачу раньше всех предыдущих?»
  2. Задачи без проверки. «Добавить состояние питомца» — не задача, а мечта: без критерия готовности вы не поймёте, закончили или нет, и агент будет додумывать за вас. Требуйте формулировку вида: «проверка: клик по кнопке увеличивает число на экране».
✓

Как проверить результат

#
✎

Практика

#

Поменяйте две соседние задачи местами и письменно ответьте, почему так нельзя (или можно — тогда объясните, зачем был исходный порядок). Ответ допишите в конец docs/plan.md под заголовком «Проверка порядка» — через месяц он объяснит вам ваш же план. Задание без готового решения: если не можете объяснить, почему нельзя поменять, — вы не понимаете свой план, вернитесь к шагу 3.

★

Главное

#
  1. План режет работу на куски с видимым результатом — это страховка от «почти правильного» кода.
  2. Порядок задач — ваша зона ответственности, агент его не гарантирует.
  3. Задача без критерия готовности — не задача.
  4. Задача, не связанная ни с функцией, ни с предпосылкой для неё, — раздувание.
  5. Если задачу нельзя проверить в браузере — она слишком большая или неправильная.
