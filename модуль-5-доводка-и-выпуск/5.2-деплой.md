# Урок 5.2. Деплой: приложение в интернете

## Зачем это нужно

Приложение в локальной папке — черновик: его видите только вы. Публикация меняет статус результата: ссылку можно отправить другу или открыть с телефона. Деплой — первое место, где агент встречается с внешним миром (платформа, чей интерфейс меняется), и потому первое место, где он массово выдумывает несуществующие кнопки и шаги. Второе звено публикации — репозиторий на GitHub: без него площадка не увидит ваш код.

## Что мы делаем

Публикуем «Пиксель» на Vercel бесплатно: выкладываем код в репозиторий на GitHub → подключаем Vercel к репозиторию → деплой → проверка с телефона. Всё в режиме «сначала план»: агент предлагает шаги, вы выполняете и подтверждаете.

## Шаг 1. Приведите репозиторий в порядок

Проверьте: все изменения закоммичены, `git status` чист, секретов в коде нет (у «Пикселя» их и не должно быть — это важный чек перед публикацией). Помните: код станет публичным, и во фронтенде всё, что попало в сборку, увидят все — правило «положить ключ в переменные окружения» тут не спасает; настоящие секреты живут только на сервере.

## Шаг 2. Опубликуйте код на GitHub

Заведите бесплатный аккаунт на GitHub (если ещё нет) и создайте пустой репозиторий `pixel-pet` — без README и .gitignore, они у вас уже есть. GitHub покажет адрес репозитория. Команды выполняете вы; агент может показать план и объяснить каждую:

```
git remote add origin https://github.com/<ваш-логин>/pixel-pet.git
git branch -M main
git push -u origin main
```

`git branch -M main` переименовывает вашу ветку в `main` — так называется ветка по умолчанию на GitHub (у вашего git настройки могут отличаться: если команда не сработает, посмотрите `git branch` и используйте своё имя). GitHub показывает два адреса репозитория — HTTPS (`https://github.com/...`) и SSH (`git@github.com:...`); в команде выше используется HTTPS, копируйте именно его.

**Первый `push` спросит доступ.** Пароль от аккаунта GitHub не подойдёт: git откроет окно Git Credential Manager (вход через браузер) или попросит логин и **токен** вместо пароля. Если окна нет, а терминал спрашивает пароль — поставьте GitHub CLI и войдите командой `gh auth login` либо создайте токен (GitHub → Settings → Developer settings → Personal access tokens) с правом на работу с репозиториями. Токен — секрет: не вставляйте его в чат агенту и не сохраняйте в файлах проекта.

После `push` обновите страницу репозитория — код на месте.

## Шаг 3. Получите план и выполняйте по шагам

Промпт ниже в режиме «ничего не выполняй, только план». План агента сверяйте с реальным экраном Vercel: интерфейс платформы меняется, и это нормально, что агент отстаёт. Где план расходится с реальностью — опишите агенту расхождение словами («на экране нет кнопки X, есть Y») и попросите скорректировать план, а не «сделай сам».

Обычно настраивать ничего не нужно: Vercel сам определяет, что это Vite, и подставляет команду сборки и папку результата. Оставьте предложенные значения — на первом деплое менять их руками не надо.

## Шаг 4. Проверьте результат с другого устройства

Откройте приложение по ссылке с телефона. Покликайте, перезагрузите, проверьте, что состояние сохраняется. Учтите: на телефоне у питомца своя копия данных — он будет в стартовом состоянии, и то, что вы кормили его на компьютере, не перенесётся. Это не баг: `localStorage` живёт в конкретном браузере на конкретном устройстве. Затем сделайте маленькое изменение (поменяйте текст), закоммитьте и **отправьте** (`git push`) — убедитесь, что оно доехало до опубликованной версии. Это цикл обновления, который вам предстоит повторять.

```
Я хочу бесплатно опубликовать это приложение (React + Vite)
на Vercel. Сначала составь план, ничего не выполняй:

2) как подключить мой репозиторий на GitHub к Vercel;
3) точный порядок действий с моей стороны;
4) типичные ошибки и как их заметить;
5) что в коде не должно попасть в публичный репозиторий.

Если в каком-то шаге не уверен (интерфейс Vercel мог
измениться) — так и скажи и укажи, где найти актуальную
инструкцию.

Дождись моего подтверждения плана.
```

## Что может пойти не так

1. **Выдуманные шаги платформы.** Агент описывает кнопки и пункты меню, которых нет на экране, — потому что его знания об интерфейсе Vercel устарели, а проверить их он не может. Не выполняйте шаг, которого не видите. «На моём экране нет этой кнопки» — законный и правильный ответ агенту.
2. **Секреты в коде.** Репозиторий и ссылка публичны: всё, что попало в сборку, увидят все. Агент может пропустить ключ в конфиге или в истории коммитов — и уверенно ответить «ключей нет». Почему: модель не чувствует границу «публичное/приватное», пока её не назвать, а слово агента — не аудит. Проверьте сами: поиск по проекту (`key`, `secret`, `token`), файлы `.env*`, при необходимости `git log`. В этом уроке ключей нет — правило для будущих проектов; и помните, что во фронтенде `VITE_`-переменные тоже попадают в публичную сборку.
3. **Push падает из-за имени ветки.** Ошибка вида `src refspec main does not match any` означает, что ваша локальная ветка называется иначе (`master`). Не угадывайте: посмотрите `git branch`, переименуйте (`git branch -M main`) и повторите `git push`.
4. **`remote origin already exists`.** У проекта уже есть удалённый репозиторий — от шаблона или от предыдущей попытки. Посмотрите `git remote -v`; чтобы заменить адрес на свой, выполните `git remote set-url origin https://github.com/<ваш-логин>/pixel-pet.git` и повторите `push`.

## Как проверить результат

- [ ] `git status` чист, все изменения закоммичены.
- [ ] Код отправлен на GitHub (`git push` прошёл, репозиторий виден в браузере).
- [ ] Вы видели и подтвердили план до его выполнения.
- [ ] Приложение открывается по публичной ссылке.
- [ ] Проверка с телефона: клики работают, состояние сохраняется.
- [ ] Новое изменение, отправленное через `git push`, доехало до опубликованной версии.
- [ ] В публичном коде нет ключей и паролей; токен доступа не отправлялся агенту в чат и не сохранён в проекте.

## Практика

Разверните приложение ещё раз — на Netlify или GitHub Pages. Задание без готового решения: цель не вторая площадка, а доказательство, что вы проходите процесс без подсказок курса, с агентом в режиме «план → подтверждение → проверка». Учтите: GitHub Pages потребует дополнительных настроек сборки — план можно спросить у агента, а сверку плана с реальностью делать как в этом уроке. Критерий: ссылка работает, и вы можете объяснить, чем путь отличается от Vercel.

## Главное

1. Деплой превращает черновик в результат, которым можно поделиться.
2. Публикация — это два звена: репозиторий на GitHub и площадка (Vercel); пропущенное звено видно сразу.
3. Интерфейс платформ меняется быстрее знаний агента — сверяйте с экраном.
4. Шаг, которого не видите, не выполняйте — даже если агент уверен.
5. Секреты и публичность — зона вашей личной проверки, а не слово агента.
6. Цикл «коммит → push → обновление» — теперь часть вашей рутины.
